系统怎么在 AWS 上整合在一起

评委的问题：这是一个调用某个接口的聊天机器人，还是一个建在 AWS 上的系统？

服务在这里做什么为什么选它
Amazon Bedrock · Claude Sonnet 5.5理解家长的需求、选择工具、写出解释题目指定；跨区域推理配置；支持提示词缓存
Amazon Bedrock · Titan Embeddings v2学校、课外项目和指南的向量和模型在同一个平台，不用再接外部服务
Amazon OpenSearch Service在 3 个索引上做硬过滤、地理范围、向量搜索和关键词搜索题目指定，也是 GreatSchools 自己的搜索平台
Amazon ECS on Fargate（ARM64）运行 Agent 的 API一轮对话要 5 到 12 秒，API Gateway 不太合适；ARM 更便宜
Amazon CloudFront + S3一个 HTTPS 地址，同时提供页面和 API不用处理跨域，也不用管证书
AWS WAF每个 IP 每 5 分钟最多 300 轮对话；屏蔽恶意 IP每一轮都要花 Bedrock 的 token
Amazon DynamoDB收藏、点赞点踩、GreatSchools 关心的指标按请求付费，空闲时几乎不花钱
IAM、CloudWatch、ECR最小权限的角色、日志、容器镜像从第一天起就可以运维
AWS CDK（Python）定义以上所有资源一条命令重建；以代码的形式便于审查

"这不是一个调用某个接口的聊天机器人。家长的每个问题都会经过 9 个 AWS 服务，全部用 CDK 定义，任何账号都能用一条命令重建。"

要花多少钱，是不是最省了？

老实说：在演示的规模下，资源规格是合理的，也已经优化过一轮。但还不是最低点，下一步怎么省，我们有实测数据。

已经做到的

提示词缓存

83% 的输入 token 来自 Bedrock 的缓存。每轮的估算成本从 0.041 美元降到 0.020 美元，速度和评测结果都没有变化。

不需要判断的地方不调用模型

修改条件、收藏、点赞点踩和查看指标都不调用模型。修改一个条件大约只要 0.2 秒。

资源规格按需选择

单节点 OpenSearch、ARM 架构的 Fargate、公有子网，不建 NAT 网关。

接下来怎么继续省（按顺序）

  1. 按任务选模型：默认用 Haiku，条件多、比较复杂的搜索再交给 Sonnet。换模型时，评测集可以保证质量不下降。
  2. 复用 GreatSchools 现有的 OpenSearch 集群，不再单独建 domain（每月约省 54 美元）。
  3. 把会话存进 DynamoDB，然后换成按调用付费的计算方式（Lambda 或 Bedrock AgentCore Runtime），不用再一直开着任务和负载均衡。
  4. 精简工具返回的数据：现在每轮大约要发送 1.1 万个 token。
按规模估算（只是举例）：每年 100 万次引导式搜索 × 每次 4 轮 = 400 万轮。 用 Sonnet 大约每年 8 万美元，用 Haiku 大约 3.4 万美元，两者混用介于两者之间。100 万次大约是 GreatSchools 每年服务的 4000 万个家庭的 2.5%。

GreatSchools 能接手继续做吗？

能，这从一开始就是设计目标。我们用的是他们的技术栈、他们的数据格式，以及他们把需求变成搜索条件的方式。

我们做了什么GreatSchools 接手时要做什么
AWS、us-east-1、OpenSearch：和他们现有的技术栈一样不用学新平台
needs 目录在 agent/gs_agent/needs.py，沿用他们"需求 → OpenSearch 参数"的设计把字段名换成他们真实索引里的字段
数据格式和他们给的样例完全一致把合成数据生成器换成他们的真实数据源，导入脚本不用改
指南内容放在一个 JSON 文件里换成他们自己的文章，代码不用改
模型跑在 Bedrock 上，并配有评测集可以放心换模型，Sonnet 和 Haiku 的对比就是例子
HTTP/JSON 接口，有书面的接口约定（docs/contract.md）从他们的 Rails 应用直接调用，或者渲染返回的 UI 块
CDK、README、12 条决策记录，加上单元测试、评测和线上接口测试能看懂每个选择背后的理由；每次修改都能马上验证
指标和他们的 KPI 一致（收藏数与搜索数之比、相关性、每次搜索的条件数）从第一天起就能和现有的搜索做 A/B 测试

从 demo 到正式上线

阶段要做的事
1 · 稳定化会话存到 DynamoDB 或 AgentCore Memory，这样才能横向扩容；改用私有子网和 VPC 端点
2 · 真实数据接入他们的 OpenSearch 和数据源；由他们的编辑审核指南内容
3 · 质量把关GitHub Actions 在每个 PR 上自动跑单元测试和评测；CloudWatch 对错误、延迟和 Bedrock 费用设告警
4 · 验证效果和现有的搜索做 A/B 测试，比较收藏数与搜索数之比
5 · Level 3用 EventBridge Scheduler 加邮件或短信，主动跟进家长

"这不是一个比赛结束就扔掉的原型。它是一个 GreatSchools 下周就能接手的起点：同样的技术栈、同样的数据格式、同样的需求映射方式，再加上一套测试，改了什么东西出了问题，马上就能知道。"
